# แก้ไขโปรโมชั่นของผู้ส่งก่อน IT บันทึกงาน

## เป้าหมายที่ผู้ใช้ยืนยัน

ผู้ส่งเปิดงานของตนเองจากศูนย์ติดตาม กลับไปฟอร์มแจ้งโปรโมชั่นเดิมพร้อมข้อมูลครบ แก้ไขและบันทึกแทนรายการเดิมได้โดยไม่กรอกใหม่ ไม่สร้างแคมเปญซ้ำ และไม่จองรหัสใหม่เพียงเพราะแก้ไข หาก IT เคยบันทึกปิดงานแล้วให้ติดต่อ IT แทน

แคมเปญทดสอบที่กู้คืนแล้ว: `TOTO - 10 คะแนน ลด 10 บาทเมนู Fries` เดือน `2026-11` มี 6 ปุ่ม 18 แถว สถานะ PENDING การทดสอบเขียนจริงต้องได้รับอนุมัติข้อมูลทดสอบก่อน ไม่เปลี่ยนราคา/รายละเอียดของงานจริงเอง

## สิ่งที่ตรวจพบ

- ศูนย์ติดตามมีหน้ารายละเอียดและการแก้ไขแบบ inline สำหรับ Admin แต่ยังไม่มีโหมดส่งกลับฟอร์มของผู้ส่ง
- CreatePromotion รวมฟอร์ม Item Set, Coupon, Bill Discount และ Voucher ซึ่งมีข้อมูลและไฟล์แนบต่างกัน
- Cloud มี commitSubmission และเลขเวอร์ชันสำหรับป้องกันข้อมูลเก่าทับข้อมูลใหม่ แต่ยังไม่มีข้อกำหนดการแทนที่แคมเปญที่ตรวจ IT-lock จากข้อมูลเดิมบนเซิร์ฟเวอร์
- ระบบปัจจุบันอ้างอิงผู้ใช้จากข้อมูลล็อกอินฝั่งเว็บและใช้ Cloud token ร่วมกัน การเทียบชื่อผู้ส่งไม่ใช่การยืนยันตัวตนฝั่งเซิร์ฟเวอร์ที่ป้องกันการปลอมแปลงได้ การเพิ่มระบบ authentication ใหม่อยู่นอกงานนี้ ต้องไม่อ้างว่าเป็นสิทธิ์ปลอดภัยสมบูรณ์

## รูปแบบการทำงาน

1. ปุ่ม “แก้ไขข้อมูล” ในรายละเอียดศูนย์ติดตามสำหรับผู้ส่งที่ตรงกับบัญชีปัจจุบัน ใช้ identity ที่มีอยู่ หากข้อมูลเจ้าของไม่ชัดเจนให้ปิดการแก้ไขและติดต่อ IT ไม่เดาเจ้าของจากบทบาท
2. ก่อนเปิดฟอร์ม อ่านแคมเปญจริงจาก Cloud รวมเดือน ข้อมูลผู้ส่ง รหัสปุ่ม เลขเวอร์ชัน และประวัติการทำงาน IT
3. เปิดฟอร์มตรงประเภทพร้อมข้อมูลสินค้า กลุ่ม SS จำนวน ราคา Net/ส่วนลด ช่องทาง สาขา วันที่ รายละเอียด เงื่อนไข และไฟล์แนบเดิม แสดงแถบ “กำลังแก้ไขรายการเดิม” กับปุ่มกลับศูนย์ติดตาม
4. ใช้บริบทแก้ไขในหน่วยความจำ ไม่เขียนสำเนาแคมเปญเป็นงานใหม่หรือเปลี่ยนฐานในเครื่องก่อน Cloud ยืนยัน เปลี่ยนหน้าโดยมีข้อมูลยังไม่บันทึกต้องเตือน
5. กดบันทึกแล้วตรวจ validation เดียวกับฟอร์มสร้างใหม่ รวม Net ที่ต้องระบุชัดเจน และข้อกำหนดไฟล์แนบ ส่ง revision ที่อ้างอิงแคมเปญ/เดือน/เวอร์ชันเดิม
6. Cloud ตรวจข้อมูลต้นฉบับและสิทธิ์ตาม identity เดิม ตรวจ IT-lock แล้วเขียนแคมเปญเฉพาะเป้าหมายพร้อมใบยืนยันแบบ transaction และ version guard ไม่เขียนทั้งฐาน การส่งซ้ำด้วย idempotency key เดิมต้องไม่สร้างงานซ้ำ
7. เมื่อ Cloud ยืนยันแล้วอ่านกลับและแสดง “บันทึกการแก้ไขสำเร็จ” อัปเดตศูนย์ติดตามและประวัติ เก็บผู้ส่ง/วันส่งเดิม พร้อมผู้แก้ไข/เวลาแก้ไขแยกต่างหาก

## IT-lock และการชนกัน

- ล็อกเมื่อพบ `itSettlementSavedAt`, `itDoneDate`, ประวัติการใช้งาน/การตรวจ OP หรือสถานะ IT COMPLETE/DONE ในขอบเขตแคมเปญที่จะเปลี่ยน ต้องไม่ปลดล็อกเพียงเพราะงานถูกตีกลับเป็น PENDING
- ข้อความ: “งานนี้ดำเนินการโดย IT แล้ว กรุณาติดต่อ IT เพื่อแก้ไขข้อมูล”
- ตรวจทั้งตอนเปิดและตอน commit; ถ้า IT ปิดงานระหว่างนั้น ต้องปฏิเสธการแก้ไขโดยไม่เขียนบางส่วน
- ถ้าเลขเวอร์ชันเปลี่ยน ให้ผู้ใช้โหลดงานล่าสุดก่อน ไม่ merge หรือส่งซ้ำทับโดยอัตโนมัติ เก็บข้อความที่กำลังแก้บนหน้าจอไว้ให้เทียบ

## รหัสและรายการปุ่ม

- งาน/ปุ่มเดิมต้องมี identity คงที่ แม้เปลี่ยนชื่อที่แสดง คง codePromotion/codeItemSet และข้อมูลยืนยันรหัสเดิม ไม่ใช้ชื่อปุ่มเป็นตัวตัดสินว่าต้องแจกโค้ดใหม่
- การเพิ่ม/ลบปุ่มระหว่างแก้ไขต้องใช้กฎจอง/คืนรหัสที่มีอยู่ ตรวจรหัสที่ใช้งานหรือใช้ร่วม และ commit พร้อมข้อมูลแคมเปญ ห้ามคืนรหัสจากปุ่มที่ใช้อยู่ในงานอื่น
- ไม่ล้าง IT/OP history เพื่อให้ผ่านเงื่อนไข ห้ามแก้แคมเปญอื่นหรือเดือนอื่นที่ไม่ได้เปิดแก้
- การเปลี่ยนชื่อแคมเปญต้องย้าย key และทะเบียนลบแบบ atomic พร้อมตรวจชื่อชน ไม่สร้างสำเนาที่ชื่อเก่ายังคงอยู่

## ความล้มเหลว

Cloud ไม่พร้อม/เครือข่ายขาด: ไม่แจ้งสำเร็จ ไม่เคลียร์ฟอร์ม ไม่ให้กรอกใหม่ทั้งหมด หาก commit สำเร็จแต่การตอบกลับขาดให้ตรวจใบยืนยันเดิมก่อนลองส่งใหม่ การเขียนฐานเบราว์เซอร์ไม่ใช่หลักฐานความสำเร็จ

## ขอบเขตไฟล์และการทดสอบ

แก้ tracking, CreatePromotion และฟอร์มทั้งสี่, ตัวกลาง Cloud, backend mapper และ Sync Worker โดยแยกจากงานแก้ race ตอนเปิดเว็บ

ทดสอบ: โหลดข้อมูลครบทุกฟอร์ม/ไฟล์/SS, แก้แล้วไม่มีงานหรือรหัสซ้ำ, แก้งานคนอื่นไม่ได้ใน UI, IT เคยปิดงาน/ตีกลับ, IT ปิดระหว่างแก้, version conflict, request ซ้ำ, เครือข่ายขาดก่อนและหลัง commit, ชื่อชน, เพิ่ม/ลบปุ่มกับรหัสร่วม และ regression ฟอร์มสร้างใหม่ ต้องทดสอบ sandbox ก่อน deploy และสำรอง Cloud ก่อนเปิดใช้จริง

## เงื่อนไขก่อนลงมือ

แบบนี้ขยายจากการเปลี่ยน UI เดิมไปถึงสัญญาการบันทึกฝั่ง Cloud จึงต้องให้ผู้ใช้ตรวจแบบนี้ก่อน แล้วจึงจัดทำแผน implementation ตามขั้นตอน architectural ของ brainstorming ไม่ถือว่าฟีเจอร์พร้อมใช้งานหรือ deploy แล้ว
